# Проблемы и их решения

### 1. Денормализованная структура БД

**Проблема:**
Таблица `tokens` содержала избыточные данные о chain и logo прямо в своих полях, что нарушало нормальные формы БД и приводило к дублированию данных.

**Решение:**
- Создал отдельные таблицы `chains` и `logos`
- Настроил правильные связи через foreign keys
- Добавил миграцию для нормализации существующих данных

**Для чего это нужно:**
Нормализованная БД проще поддерживать, она занимает меньше места и исключает аномалии обновления.

### 2. Хардкод конфигурации

**Проблема:**
Параметры подключения к БД и Kafka были захардкожены прямо в коде, что делало невозможным запуск в разных окружениях.

**Решение:**
- Создал конфигурацию через environment переменные
- Добавил валидацию конфигурации при старте

**Для чего это нужно:**
Теперь можно легко деплоить приложение в разных окружениях (dev, staging, prod) без изменения кода.

### 3. Отсутствие обработки ошибок

**Проблема:**
Сервисы не обрабатывали ошибки, что приводило к падению всего приложения при любой проблеме.

**Решение:**
- Добавил try-catch блоки во все критические места
- Реализовал retry механизм с exponential backoff для внешних вызовов
- Добавил глобальный exception filter для унифицированной обработки ошибок

**Для чего это нужно:**
Приложение стало устойчивым к временным сбоям внешних сервисов и не падает при единичных ошибках.

### 4. Отсутствие DTO и валидации

**Проблема:**
Прямое использование entities во всех слоях приложения, отсутствие валидации входных данных.

**Решение:**
- Создал DTO для каждой операции (Create, Update, Response)
- Добавил валидацию через class-validator
- Внедрил mapper для преобразования Entity в DTO

**Для чего это нужно:**
Четкое разделение слоев, автоматическая валидация данных, защита внутренней структуры БД от изменений API.

### 5. Последовательная обработка токенов

**Проблема:**
Обновление цен происходило строго последовательно, что сильно замедляло процесс при большом количестве токенов.

**Решение:**
- Добавил возможность параллельной обработки через конфигурацию
- Реализовал батчевую обработку с настраиваемым размером пакета
- Добавил логирование времени выполнения для мониторинга

**Для чего это нужно:**
Скорость обновления цен увеличилась в разы при включении параллельного режима.

### 6. Проблемы с гарантией доставки сообщений

**Проблема:**
При сбое Kafka терялись сообщения об обновлении цен.

**Решение:**
- Реализовал Transactional Outbox паттерн
- Сообщения сначала сохраняются в БД, затем асинхронно отправляются в Kafka
- Добавил retry механизм для failed сообщений

**Для чего это нужно:**
Гарантия доставки критически важных бизнес-событий даже при временной недоступности Kafka.

### 7. Неправильные типы данных

**Проблема:**
- price хранилась как decimal(28,0) - без дробной части
- address хранился как bytea вместо строки

**Решение:**
- Изменил price на decimal(18,8) для хранения дробных значений
- Конвертировал address из bytea в varchar с hex представлением

**Для чего это нужно:**
Правильные типы данных критичны для корректной работы с финансовыми данными.

### 8. Отсутствие индексов БД

**Проблема:**
Запросы могут выполняться медленно в том числе из-за отсутствия индексов.

**Решение:**
Добавил индексы для:
- Уникальный составной индекс (address, chainId)
- Индекс на chainId для оптимизации JOIN
- Индекс на lastPriceUpdate для сортировки
- Covering индекс для батчевой обработки

**Для чего это нужно:**
Индексы критичны для производительности при росте объема данных.

### 9. Отсутствие тестов

**Проблема:**
Код не был покрыт тестами.

**Решение:**
- Создал unit тесты для всех сервисов
- Настроил mock'и для внешних зависимостей

**Для чего это нужно:**
Тесты дают уверенность при внесении изменений и служат документацией к коду. Стандартная практика при написании сервисов.

## Дополнительные решения:

### 10. Потенциальная гонка данных

**Проблема:**
При параллельной обработке разные батчи могут одновременно обновлять один токен.

**Решение:**
- Использовал SELECT FOR UPDATE внутри транзакции для блокировки токена
- При обновлении токена используется pessimistic write lock
- Добавил обработку deadlock и lock timeout ситуаций с автоматическим retry
- Короткие задержки для lock conflicts, длинные для других ошибок
- Если токен заблокирован, он пропускается и обрабатывается в следующем цикле

### 11. Неограниченный рост таблицы Outbox

**Проблема:**
Успешно отправленные события помечались как SENT, но никогда не удалялись из БД, что приводило к неограниченному росту таблицы.

**Решение:**
- Успешно отправленные события теперь удаляются сразу после отправки в Kafka
- Добавлена периодическая очистка старых failed событий (старше 24 часов по умолчанию)
- Настраиваемый интервал очистки и время хранения через конфигурацию
- Это предотвращает неконтролируемый рост БД при сохранении истории для отладки

## Потенциальные улучшения (не реализованы):

### Рефакторинг

 - В каждой сущности выделить свои контроллеры, сервисы и создать свой nest-модуль для более легкой интеграции в основную фабрику приложения

### Мониторинг
 - Добавление Healthcheck
 - Подключение New Relic/Sentry

## Архитектурные улучшения

### 1. Dependency Injection
Использовал DI контейнер NestJS для управления зависимостями. Это упростило тестирование и сделало код более модульным.

### 2. Separation of Concerns
Четко разделил ответственности:
- Entity - структура БД
- DTO - контракты API и валидация
- Service - бизнес-логика
- Mapper - преобразование между слоями

### 3. Configuration
- Вся конфигурация вынесена в отдельный модуль с типизацией и валидацией
- Вместо передачи всего конфига передается только необходимая его чать

### 4. Graceful Shutdown
Добавил корректное завершение работы с очисткой ресурсов (закрытие соединений с БД и Kafka).


## Результаты

1. **Надежность**: Сервис стал устойчив к сбоям внешних систем
2. **Производительность**: Параллельная обработка ускорила обновление цен в несколько раз
3. **Поддерживаемость**: Чистая архитектура и тесты упростили дальнейшую разработку
4. **Масштабируемость**: Можно легко добавить новые источники цен или типы токенов
5. **Мониторинг**: Детальное логирование позволяет отслеживать работу системы
6. **Конкурентность**: Решена проблема race conditions при параллельной обработке
